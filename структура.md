# Структура ВКР: «Исследование и разработка веб-приложения для совместного учёта расходов»

Направление: 09.04.02 «Информационные системы и технологии», профиль «Веб-разработчик».
Стек: React 19 + Vite (SPA), FastAPI, PostgreSQL, RabbitMQ, Nginx, Docker.
Объём основной части: 60–100 стр. Экспериментальная часть не предусмотрена.

Структура работы — три раздела (по чек-листу ВКР 2026 НИТУ МИСиС): теоретические основы и проектирование → реализация и тестирование → анализ результатов и направления развития. В каждом разделе 2–4 подраздела с краткими выводами после каждого подраздела и обобщёнными выводами в конце раздела. После раздела 1 обобщённые выводы вынесены в отдельный файл `1_8_выводы_по_разделу_1.md`. Введение работы дополнительно описывает содержание каждого раздела.

## Глава 2. Реализация и тестирование веб-приложения (~25–32 стр.)

После введения раздела 3 объём главы 2 сокращён: блок «оценка результатов и направления развития» (бывший §2.5) перенесён в §3.1, §3.3, §3.4. В §2.4 оставлена только таблица соответствия реализации требованиям F1–F8 / NF1–NF6 как факт реализации; интерпретация и направления развития — в разделе 3.

### 2.1 Реализация серверной части приложения (~10–12 стр.)
- Структура проекта: слои, точка входа, dependency injection, общие модули (`common/`)
- auth-service: JWT RS256 в `jwt_tokens.py`, cookie-параметры (`httponly`, `samesite`), token-family rotation в `service.py`, чтение cookies в `/auth/refresh`; реализует схему §1.4.2
- api-gateway: валидация JWT, формирование `X-User-Id` / `X-User-Roles`, удаление входящих `X-User-*` заголовков; реализует §1.4.1
- groups-service: создание группы в одной транзакции, ролевая модель, приглашения по `target_user_id`; `audit_log`
- expenses-service: split engine (equal/custom, floor + остаток первому), balance engine (`_calculate_balances_from_records`), greedy-минимизация (`_simplify_balances_from_records`, не более N−1), `idempotency_keys` с составным PK и `response_body`; реализует модель §1.6.5–§1.6.6
- outbox-worker: чтение `pending` из `expenses.outbox`, публикация в `app.events`, повторная доставка; реализует паттерн §1.4.3
- notify-service: идемпотентная обработка через `processed_events`, DLQ, `EMAIL_BACKEND=logging/smtp`
- Работа с PostgreSQL: SQLAlchemy 2.0 async, Alembic, Make-цели применения миграций (`auth-migrate`, `groups-migrate`, `expenses-migrate`, `notify-migrate`), schema-guard (`common/schema_guard.py`, `readiness.py`, healthcheck)

### 2.2 Реализация клиентской части приложения (~8–10 стр.)
- Структура React SPA: React Router 7 (data-режим), организация компонентов и хуков, сборка Vite
- Состояние: TanStack Query (серверное состояние, кеш, инвалидация при polling) + Zustand (auth/client state)
- Взаимодействие с API: обработка 401 → redirect, обработка ошибок, idempotency в клиенте
- Сценарии пользователя с иллюстрациями: регистрация/вход, создание группы и приглашение участника, добавление расхода (equal/custom split), просмотр балансов и упрощённых взаиморасчётов, погашение долга (settlement), история операций

### 2.3 Реализация инфраструктуры развёртывания (~5–6 стр.)
- Docker Compose dev vs. prod: принципиальные отличия (публикация портов, restart-политика, `ports: !reset []` в prod)
- Nginx: `nginx.conf` (dev) и `nginx.prod.conf` (prod — rate-limit зоны `auth_login_zone` 5 r/m и `auth_refresh_zone` 30 r/m, TLS 1.2/1.3, HTTP→HTTPS redirect), bootstrap-конфиг для первичного выпуска сертификата; конфиги целиком — в приложения
- TLS и certbot: certbot-сервис с периодом обновления 12 ч, монтирование `/etc/letsencrypt`, HTTP-01 challenge
- systemd-юниты: `vkr-project.service`, `vkr-project-backup.service`, `vkr-project-backup.timer`
- Резервное копирование PostgreSQL: `backup-postgres.sh`, ротация 14 суток; ограничение MVP — копии только на том же VPS
- Порядок развёртывания на VPS: `git clone` → `.env` → `make *-migrate` → `docker compose up`; schema-guard как механизм готовности перед приёмом трафика

### 2.4 Тестирование и оценка соответствия требованиям (~6–7 стр.)
- Стратегия: unit (финансовая модель) + integration (сервисный слой с реальной тестовой базой) + smoke (healthcheck после `docker compose up`); e2e frontend — включать только при наличии в репозитории
- Тестирование финансовых инвариантов: split engine (equal, custom, остаток первому), balance engine (`sum=0`, транзитивность), greedy-минимизация (N−1, пример на 4 участниках)
- Тестирование auth/security: token-family rotation, детекция компрометации, cookie-параметры; уточнить — unit или integration с реальной базой
- Quality gate: покрытие, линтеры, автоматизация
- Таблица результатов тестирования (подробная версия — в Приложение Г)
- Таблица соответствия реализации требованиям: F1–F8, NF1–NF6 → где реализовано → статус (реализовано / реализовано частично / в v2)
- **Выводы по разделу 2** (специально оформлены)

## Глава 3. Анализ результатов разработки и направления развития системы (~20–23 стр.)

Раздел вводится для соответствия чек-листу ВКР 2026 НИТУ МИСиС (требование трёх разделов основной части). Содержательно — это анализ результатов реализации, сопоставление с альтернативными подходами, технико-экономическая оценка и обоснование направлений развития системы. Закрывает критерий оценки «отлично» из методички (Приложение З): анализ способов реализации поставленных задач и оценка эффективности их внедрения.

### 3.1 Анализ результатов реализации архитектурных решений (~5–6 стр.)
- Открывающий абзац: в разделах 1 и 2 решены задачи 1–8 введения; настоящий раздел посвящён анализу полученных результатов, их сопоставлению с альтернативными подходами и формулировке направлений дальнейшего развития
- Анализ ключевых архитектурных вызовов, выявленных в ходе реализации: согласованность данных при сбоях (Outbox + at-least-once + processed_events), разграничение зон доверия (api-gateway как единая точка проверки JWT), идемпотентность мутаций (составной ключ + response_body), корректность округления долей при делении неделимых сумм (распределение остатка первому участнику)
- Принятые в ходе разработки компромиссы и их обоснование: отказ от `balance_snapshot` в MVP, локальное хранение бэкапов, отсутствие zero-downtime-релизов, cross-schema чтение `memberships` как осознанное исключение
- Опора на результаты главы 2 (фактическую реализацию), а не на проектные намерения главы 1

### 3.2 Сопоставление реализованной системы с альтернативными подходами (~5–6 стр.)
- Event Sourcing и CQRS как альтернатива транзакционной модели с Outbox — какие именно ограничения MVP были бы сняты переходом на event-sourcing, какие издержки повлёк бы такой переход
- Saga-pattern и распределённые транзакции как альтернатива cross-schema чтению `memberships` в одной БД — обоснование, почему для MVP в одной БД на одном VPS такой переход избыточен
- Change Data Capture как альтернатива паттерну Outbox — операционные предпосылки, которые делают CDC экономически нецелесообразным для рассматриваемой нагрузки
- Partitioning и sharding PostgreSQL как путь горизонтального масштабирования — какие изменения схемы потребуются
- Опора на источники из библиографии: [4] Kleppmann, [36] Newman, [7] Rahmatulloh и др.; при необходимости расширить библиографию 2–3 источниками по CDC и federated identity

### 3.3 Технико-экономическая оценка результатов (~4–5 стр.)
- Трудозатраты на разработку по компонентам (часы / story points, по данным git log и оценке)
- Стоимость VPS-инфраструктуры за 12 месяцев (тариф, объём ресурсов)
- Сравнение совокупной стоимости владения с подписочной стоимостью аналогов (Splitwise Pro ≈ $3/мес., Tricount Premium ≈ €2.5/мес.) на горизонте 12 месяцев — для группы из N пользователей
- Метрики качества: покрытие тестами (line / branch), доля property-based тестов в общем объёме тестирования, время отклика основных эндпоинтов (`POST /expenses`, `GET /balances/simplified`)
- Оценка технической эффективности — соответствие задачам ВКР через ссылку на таблицу F1–F8 / NF1–NF6 из §2.4

### 3.4 Направления развития системы (~4–5 стр.)
Для каждого направления указывается: (а) текущее ограничение MVP, (б) технические предпосылки в реализованной архитектуре, (в) необходимые изменения, (г) оценка сложности реализации.
- `balance_snapshot` и read-through кэширование агрегированных балансов
- Blue-green-релизы и подготовка к zero-downtime развёртыванию
- Горизонтальное масштабирование backend-сервисов (вне expenses-worker и notify-service)
- Внешнее хранилище резервных копий (S3-совместимое объектное хранилище)
- Federated identity и интеграция с внешними провайдерами аутентификации
- Расширенная аналитика расходов (агрегаты, прогнозы, экспорт)
- Мобильное приложение / адаптация интерфейса под мобильные устройства
