## Часть II. Сомнительные привязки в тексте

Список мест, где источник плохо соответствует тематике утверждения. Цитата → источник → проблема → рекомендация.

### II.1. Чрезмерное и нетематичное использование [5] Kleppmann

Книга «Designing Data-Intensive Applications» цитируется ~13 раз. В 5–6 из них тематика выходит за пределы книги.

1. **§1.4 строка 62 + §1.6 строка 37 — refresh-token rotation / OAuth 2.0**
   > «Данный подход реализует рекомендацию OAuth 2.0 по детектированию повторного использования refresh token [5]»
   У Kleppmann нет раздела про OAuth refresh-tokens. Корректный источник — RFC 6749 / RFC 6819 / draft-ietf-oauth-security-topics. В библиографии нет — нужно добавить новый источник, либо снять ссылку.

2. **§1.5 строка 52 + §1.6 строка 101 — финансовая арифметика / floating point**
   > «Применение чисел с плавающей точкой для финансовых расчётов недопустимо ввиду накопления ошибок [5]»
   Kleppmann про денежную арифметику не пишет. Это общеинженерное знание. Уместнее [9] Tezuysal (PostgreSQL/MySQL design book) с упоминанием `NUMERIC`/`DECIMAL`, или вообще без ссылки.

3. **§1.5 строка 120 — воспроизводимость миграций**
   > «Это исключает ситуации, при которых схема на продуктовом сервере расходится со схемой, описанной в коде [5]»
   У Kleppmann нет специальной главы про schema-as-code и Alembic. Уместнее [24] Alembic или [30] SQLAlchemy.

4. **§1.7 строка 15 — поверхность атаки**
   > «...сокращает поверхность атаки до одного публично доступного процесса [5]»
   Тема network/web security и attack surface не центральна у Kleppmann. Уместнее OWASP или общая литература по security.

5. **§1.3 строка 110 — Kafka vs RabbitMQ для малых нагрузок**
   > «...для разрабатываемой системы с ожидаемой нагрузкой на несколько порядков меньше эти издержки нецелесообразны [5]»
   Kleppmann описывает Kafka нейтрально, прямой рекомендации «не выбирайте Kafka для малых проектов» нет. Это инженерное обобщение автора, а не цитата.

### II.2. [13] FastAPI docs для общих принципов REST

1. **§1.6 строка 7 — REST как стиль**
   > «...архитектурный стиль REST, широко применяемый при проектировании программных интерфейсов веб-приложений [13]»
   REST как архитектурный стиль — это Roy Fielding (2000), а не FastAPI docs. FastAPI docs упоминает REST, но не «обосновывает» его.

2. **§1.6 строка 9 — версионирование URL vs header**
   > «Версионирование через сегмент пути предпочтено... как более очевидный и легко тестируемый способ [13]»
   FastAPI docs не делает категоричной рекомендации по версионированию URL vs header. Это общая практика API design либо собственное проектное решение автора.

### II.3. [6] Martin для Repository pattern

**§1.3 строка 155** — «Repository pattern применён в notify-service... [6]».
Repository pattern относится к E. Evans (DDD) или M. Fowler (PoEAA), а не к Clean Architecture Мартина.

### II.4. [16] PostgreSQL docs для списка промышленных применений

**§1.3 строка 94** — «Среди промышленных применений упоминаются [16]».
PostgreSQL docs не содержит официального списка production-пользователей. Утверждения о Reddit, Instagram и т.д. обычно ссылаются на отдельные пресс-релизы.

### II.5. [40] OWASP Password Storage для XSS защиты refresh-токена

**§1.6 строка 33** — «Размещение refresh-токена в cookie, недоступной JavaScript-коду, предотвращает его извлечение через XSS-уязвимости [40]».
Password Storage Cheat Sheet касается хранения паролей. Для refresh-token в HttpOnly cookie уместнее OWASP **Session Management Cheat Sheet** или OAuth Security Topics.

### II.6. [15] React docs для Nginx

**§1.4 строка 13** — «...статический бандл отдаётся через Nginx [15]».
React docs не описывает деплой через Nginx. Уместнее [43] Vite (build) или [23] Nginx (serving static).

### II.7. [45] Splitwise Engineering Blog без конкретного поста

**§1.3 строка 98** — «...сервис Splitwise, применяющий PostgreSQL для учёта совместных расходов [45]».
Ссылка `https://blog.splitwise.com/category/dev-blog/` — это категория, а не конкретная статья. Утверждение о PostgreSQL в Splitwise должно подтверждаться конкретной публикацией. Кандидат на замену конкретным постом или удаление утверждения.

### II.8. [33] Ubuntu Server Guide — слишком общий для SSH-hardening

**§1.7 строка 29** — «...практики hardening, изложенные в руководстве администратора Ubuntu Server [33]».
SSH-ключи, отключение root-входа — общая SSH best practice, частично описанная в Ubuntu Server Guide. Источник формально подходит, но привязка этикетная.

### II.9. [36] НАФИ для технического требования NF2

**§1.1 строка 119** — «**NF2.** Поддержка веб-интерфейса, доступного с настольных и мобильных устройств без установки нативного приложения [36]».
Данные НАФИ о 16 приложениях косвенно обосновывают желательность веб-доступа, но не подтверждают именно требование «без установки». Привязка ослаблена.

### II.10. [4] Girdhar для «массовых пользовательских практик»

**§1.1 строка 23** — «...по результатам анализа массовых пользовательских практик и публикаций по тематике [4, 11]».
Одна IEEE-статья для подтверждения «массовых пользовательских практик» — слабый источник. Связь с конкретным тезисом не раскрыта.

### II.11. [1] Banks A. как формальное упоминание

**§1.3 строка 74** — «...поэтому базовой библиотекой клиентской части принят React [1, 15]».
Книга Banks упомянута единственный раз без конкретного аргумента, который мог бы быть только из неё. Книга 2020 года для React 19 — частично устаревший источник для специфики версии. Либо раскрыть связь, либо снять ссылку.

### IV.1. Неправильная разбивка ISBN-13 на блоки

В четырёх книжных источниках ISBN-13 разбит на блоки некорректно (правильную разбивку можно проверить на isbn-international.org или взять с обложки):

|---|---|---|
| 5 | `978-1-449-37332-0` | `978-1-4493-7332-0` |

| 9 | `978-1-803-23347-5` | `978-1-80323-347-5` |
| 10 | `978-1-803-24596-6` | `978-1-80324-596-6` |

### IV.2. «arXiv preprint» избыточно в [3], [7]
