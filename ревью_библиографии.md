## Часть II. Подозрительные привязки в тексте

Список конкретных мест, где источник плохо соответствует тематике утверждения. Цитата → источник → проблема → рекомендация.

### II.1. §1.6:143 — «аналогичный подход» сглаживает алгоритмическое различие

> «Аналогичный подход к упрощению долгового графа применяется в сервисе Splitwise [13] и описан в работе [2]»

**Проблема.** Mohan [13] описывает у Splitwise **max-flow на residual graph** (теория графов, Edmonds–Karp / Dinic). Наш алгоритм — **жадный по нетто-сальдо** с границей $N-1$. Это **разные алгоритмы**. В §1.3:11 это противопоставление сделано корректно, но в §1.6:143 «аналогичный подход» сглаживает разницу. Аналогично [2] Gavrila — это специфический алгоритм клиринга для межкорпоративных обязательств в Минэкономики Румынии.
**Рекомендация:** переформулировать — «к близкому классу задач относятся подходы, реализованные в Splitwise [13] и описанные в [2]» или «задачи того же класса рассмотрены в работах [2, 13]».

### II.2. §1.1:119 — [29] НАФИ для технического требования NF2

> «**NF2.** Поддержка веб-интерфейса, доступного с настольных и мобильных устройств без установки нативного приложения [29]»

**Проблема.** Статистика НАФИ описывает количество установленных приложений (≈16 шт.) и долю пользователей различных категорий сервисов. Из неё **не следует** требование «работать без установки нативного приложения». Логический скачок: «у пользователей много приложений → давайте делать без приложения». Источник правомерен в строках 3, 29 (общая статистика), но в строке 119 он не обосновывает именно NF2.
**Рекомендация:** снять [29] из строки 119 или переформулировать NF2 как проектное решение без претензии на эмпирическое обоснование.

### II.3. §1.3:39 — [8] Tezuysal как «литература по системам с финансовой моделью»

> «выбор которой соответствует литературе по системам с финансовой моделью и нетривиальной структурой агрегатов [8]»

**Проблема.** Источник [8] — общий учебник по проектированию БД на PostgreSQL/MySQL, не специализированный по финансовым системам. Формулировка преувеличивает охват книги.
**Рекомендация:** убрать эпитет «финансовая модель» — использовать источник как опору общего выбора PostgreSQL для нетривиальных агрегатов. Привязка в §1.5:11 и §1.5:86 — корректна.

### II.4. §1.3:11 — [48] IJFMR как «академическая литература»

> «представлен как самостоятельная методология проектирования сплит-трекеров и в академической литературе [48]»

**Проблема.** IJFMR — open access журнал без жёсткого рецензирования (не входит в Scopus/WoS, заявленный impact factor завышен). Называть статью оттуда «академической литературой», на которую опирается обоснование архитектурного выбора, — методически спорно. Содержательно ссылка уместна (статья описывает жадный по net balance), но статус источника не соответствует слову «академическая».
**Рекомендация:** смягчить — «обсуждается в недавних публикациях [48]» или «представлен в открытых публикациях по тематике» без слова «академическая».

### II.5. §1.4:9 — [22] Nginx docs для очистки X-User-*

> «Nginx очищает входящие HTTP-заголовки семейства `X-User-*`, предотвращая передачу клиентом поддельных идентификационных данных во внутреннюю сеть [22]»

**Проблема.** Документация Nginx описывает директивы `proxy_set_header`, `more_clear_input_headers`, но **не доктрину** «очистка undefined-заголовков для защиты от подделки идентичности». Это прикладной приём, а ссылка [22] — на доку модуля.
**Рекомендация:** дополнить источником по zero-trust / API-gateway hardening (например, [30] Newman) или оставить [22] только для подтверждения технической возможности, переформулировав текст.

### II.6. §1.3:43 — [17] (landing) для подтверждения SPA-архитектуры Splitwise

> «Splitwise также распространяется как SPA-приложение поверх описанного выше Rails-API [17]»

**Проблема.** Официальный landing-сайт Splitwise не «подтверждает» что это SPA — это эмпирическое наблюдение из браузера.
**Рекомендация:** перенести опору на [40] (engineering blog) или [42] (job description), уже использованные для подтверждения Rails-стека.

## Часть IV. Сводные проблемы оформления

### IV.1. Инициалы с пробелами по ГОСТ

В нескольких источниках инициалы записаны слитно: [5] «R.C. Martin» → должно быть «R. C. Martin», [9] «S.J.C. Tragura» → «S. J. C. Tragura», [10] «D.E. Yurochkin» → «D. E. Yurochkin», [3] «G. Girdhar» — корректно.

### IV.2. IEEE-источники без URL и даты обращения

В [3], [7], [10] отсутствуют:
- URL `https://doi.org/{DOI}` или прямой `ieeexplore.ieee.org/document/{ID}`;
- дата обращения;
- место проведения конференции (Bandung для ICADEIS, Moscow для ElConRus);
- издатель (IEEE);
- страницы статьи в материалах конференции.

### IV.3. Препринт arXiv vs рецензируемая публикация

[6] Pătcaș — есть **рецензируемая публикация**: Acta Universitatis Sapientiae, Informatica, 2011, Vol. 3, No. 2, pp. 192–204. В библиографии указан только arXiv-препринт. Методически правильнее использовать рецензируемую версию.

### IV.4. Двойной редирект

[25] SQLAlchemy — `https://docs.sqlalchemy.org` → `/docs/stable/` → `/20/`. Заменить на стабильный `https://docs.sqlalchemy.org/en/20/`.

### IV.5. Нарушение алфавитного порядка в составной ссылке

§1.4:13 — `[35, 24]` (TanStack Query + Zustand) — нарушает возрастающий порядок номеров. Должно быть `[24, 35]`.
