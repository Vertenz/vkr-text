# 1.3 Архитектурный анализ аналогов и обоснование технологического стека

Функциональное сравнение в §1.2 показало, что ни одно из существующих решений не удовлетворяет совокупности требований: групповые расчёты с минимизацией взаиморасчётов, русскоязычная локализация, открытый исходный код и возможность самостоятельного развёртывания. Это обосновало необходимость собственной разработки, но оставило открытым вопрос, какие инженерные практики стоят за рассмотренными продуктами и какие из них применимы к проектируемой системе.

Предметом архитектурного анализа служат те же системы, которые сопоставлены функционально в §1.2, но рассматриваемые со стороны стека и инженерных решений. Источники различаются по степени раскрытости: одни компании публикуют технологический блог и open-source библиотеки, другие распространяют только сам продукт. Поэтому анализ доступной части аналогов соединяется с обоснованием выбранного стека: каждое архитектурное решение соотносится либо с подтверждённой практикой отрасли, либо с устранимым ограничением рассмотренных продуктов. По результатам подраздела фиксируется набор технологий, на котором строится последующее проектирование архитектуры (§1.4).

## 1.3.1 Архитектуры зарубежных аналогов

**Splitwise.** Серверная часть Splitwise построена на Ruby on Rails. Это подтверждается инженерным блогом компании, в котором публикуются заметки об оптимизации Rails-приложения, ускорении расчёта балансов и оптимизации длинных SQL-запросов к финансовым агрегатам [40]. Один из открытых артефактов команды — гем `cacheable`, инкапсулирующий аспектно-ориентированное кеширование значений тяжёлых методов на стороне Rails-приложения; в публикации отмечается, что именно этот инструмент позволил очистить и упростить логику кеширования балансов в продакшен-коде Splitwise [40, 41]. Совокупность этих публикаций позволяет отнести бэкенд Splitwise к классу монолитных Ruby on Rails-приложений с интенсивным кешированием агрегатов поверх реляционной базы данных.

Клиентская часть и инфраструктурная привязка Splitwise документированы менее подробно. Открытые источники подтверждают использование Redux, Bootstrap и jQuery на фронтенде, а также Cloudflare в качестве сетевого уровня перед приложением [42]; провайдер хостинга публично не раскрывается, что само по себе указывает на закрытость инфраструктуры. Архитектура Splitwise задаёт два значимых для настоящей работы ориентира. Первый — необходимость отделять тяжёлую агрегацию балансов от обработки запросов и кешировать её результаты: при росте истории расходов прямой расчёт по операционным таблицам становится узким местом, и зрелый продукт явно адресует эту проблему. В проектируемой системе на текущем масштабе агрегаты вычисляются по запросу, а кеш агрегированных балансов через материализованный снимок (`balance_snapshot`) зафиксирован как направление развития (§1.4.4). Второй ориентир — устойчивость связки «реляционная СУБД и приложение с собственным слоем кеширования», подтверждающая применимость аналогичного подхода без перехода на BaaS-платформу.

**Settle Up.** Settle Up, разработанный чешской компанией Step Up Labs, построен на платформе Firebase: серверная сторона представлена облачными функциями (Cloud Functions) и хранилищем Realtime Database, клиентские приложения — на Angular для веб-версии и нативных мобильных каркасах для iOS и Android. Стек Angular + Firebase Realtime Database характерен для проектов команды Step Up Labs: в заметке Д. Вавры о побочном проекте mdevCoinExchange описывается шаблон работы Angular-клиента с Realtime Database через реактивные подписки, применимый и к Settle Up [43].

Каналом доставки уведомлений до клиентов Settle Up служит Firebase Cloud Messaging — управляемый web-push-сервис, интеграция с которым описана в публикации Ф. Прохазки и снимает с команды задачу поддержки собственного push-инфраструктурного слоя [44]. Описанный стек обеспечивает быстрый запуск продукта: BaaS-платформа берёт на себя хранение данных, аутентификацию, web-push и масштабирование. Цена этой простоты — жёсткая привязка к одному провайдеру: переход на self-hosted развёртывание требует параллельной реализации того, что в продукте делегировано Firebase. Именно эта зависимость объясняет, почему даже при наличии русскоязычной локализации (§1.2) Settle Up не закрывает требование контроля данных силами самой группы пользователей.

Архитектура Settle Up задаёт два прикладных ориентира. Web-push как канал уведомления участников группы — индустриально проверенное решение для трекеров совместных расходов; в проектируемой системе оно реализовано через собственный notify-service, хранящий подписки в `push_subscriptions` и фиксирующий факт доставки в `notification_deliveries` (§1.5.5), что воспроизводит наблюдаемый у Settle Up результат без зависимости от Firebase. Замена BaaS-инфраструктуры собственными сервисами оправдана при наличии явного требования к независимости развёртывания — оно выведено в §1.2 и определяет последующий выбор технологий в подразделе 1.3.3.

## 1.3.2 Архитектуры отечественных аналогов

**Дзен-мани.** Дзен-мани строится вокруг открытого REST API, через который выполняется автоматический импорт банковских операций и который доступен внешним разработчикам. Существование и стабильность этого интерфейса подтверждаются open-source инструментами, использующими его напрямую: утилита `zenmoney-backup` периодически экспортирует данные пользователя в JSON через OAuth-токен и публикуется в виде Docker-образа, а её исходный код демонстрирует устойчивые контракты запросов, схему получения токена через зеркальный сервис `zerro.app/token` и формат возвращаемых сущностей [45]. Дополнительно в техническом блоге А. Свиридова сравнение нескольких приложений для личных финансов завершается выбором Дзен-мани из-за того, что импорт операций через банковский API оказывается надёжнее парсинга SMS-уведомлений [46]. Таким образом, граница системы документирована достаточно, чтобы вокруг неё возникли внешние клиенты, тогда как внутренняя реализация остаётся закрытой.

Для проектируемой системы это означает, что наличие машинно-читаемого описания API имеет прямой прикладной смысл. В принятом стеке такую роль выполняет автоматически генерируемая спецификация OpenAPI, которая формируется FastAPI на основе Pydantic-схем без поддержки отдельного документа (§1.5.8) и фиксирует контракт между серверной и клиентской частями приложения.

**CoinKeeper.** Сам продукт закрыт, что затрудняет прямой архитектурный анализ. В открытом доступе, однако, существуют реализации expense-tracker-приложений того же класса, показывающие, какой набор технологий считается современным стандартом. Open-source проект `mk-manishkumar/coinkeeper` опубликован с явным указанием стека: фронтенд на React и TypeScript с подключением Tailwind CSS и Redux Toolkit, бэкенд на Node.js и Express с MongoDB через Mongoose, аутентификация через JWT и bcryptjs [47]. Совпадение клиентского стека (React + TypeScript + Tailwind) с принятым в проектируемой системе подтверждает распространённость такого выбора для веб-приложений учёта расходов; серверный стек Node.js/Express, напротив, отличается от выбранного FastAPI на Python, и обоснование этого расхождения раскрывается в подразделе 1.3.3.

**Tricount, Splid, банковские инструменты.** Архитектура этих систем публично не документирована: Tricount после приобретения цифровым банком bunq интегрирован в его инфраструктуру и технические заметки прежней команды более не публикуются; Splid — закрытое мобильное приложение Team Turtle, не сопровождаемое инженерным блогом; встроенные функции разделения платежей в приложениях Т-Банка и Сбербанка являются частью корпоративных банковских систем. Архитектурный анализ ведётся только по тем системам, для которых стек подтверждается независимыми источниками; функциональные характеристики Tricount, Splid и банковских инструментов зафиксированы в §1.2.

## 1.3.3 Технологический стек разрабатываемой системы

Рассмотренные архитектуры дают три точки сопоставления: серверный язык и фреймворк, способ хранения данных и канал асинхронной доставки событий, клиентский стек и режим рендеринга. По каждой из них принят набор технологий, опирающийся на индустриальную практику и одновременно устраняющий выявленную в §1.2 зависимость от чужой инфраструктуры.

**Серверная часть: FastAPI, Python, PostgreSQL, RabbitMQ.** В качестве серверного фреймворка принят FastAPI [12], построенный поверх ASGI-каркаса Starlette и библиотеки декларативной валидации Pydantic. Pydantic-схемы одновременно проверяют входящие запросы и формируют спецификацию OpenAPI [26], используемую как источник типов для клиентского приложения; на этом построен инвариант суммы долей в `PATCH /expenses/{id}`, возвращающий код `422` ещё до входа в сервисный слой (§1.5.12). Применимость FastAPI к набору независимо разворачиваемых сервисов с раздельными базами и обменом событиями подтверждается специализированной литературой по разработке микросервисов на Python [9].

В сравнении с Ruby on Rails (стек Splitwise) и Node.js/Express (стек open-source реализации CoinKeeper-подобного приложения [47]) Python с FastAPI выбран по трём соображениям: встроенный модуль `decimal` для арифметики с фиксированной точкой при работе с минимальными денежными единицами и контролем округления долей (§1.6); декларативная валидация на Pydantic, снимающая рассинхронизацию между схемами и документацией API; нативная поддержка `async/await` без обёрток `sync_to_async`, типичных для классических синхронных Python-фреймворков.

В качестве реляционной СУБД принята PostgreSQL 16 [15], выбор которой соответствует литературе по системам с финансовой моделью и нетривиальной структурой агрегатов [8]. Востребованы три её возможности: ACID-транзакции, на которых строится атомарная запись расхода и outbox-события в одной транзакции (§1.4.3); тип JSONB для полей `outbox.payload`, `activity_log.data` и `idempotency_keys.response_body`; частичные уникальные индексы, на которых построены инварианты `uq_auth_refresh_one_active_per_family WHERE status = 'active'` и выборка непрочитанных уведомлений через `ix_notifications_user_unread` (§1.5.2, §1.5.5). Логическое разделение между сервисами обеспечивается схемами `auth`, `groups`, `expenses`, `notify` в одном экземпляре базы — это сохраняет переносимость кода для перехода к отдельной БД на сервис. Управление миграциями выполняется через Alembic [23], интегрируемый с SQLAlchemy [25].

Брокером сообщений выбран RabbitMQ [16], реализующий протокол AMQP 0-9-1. Подтверждения доставки и `durable`-очереди обеспечивают семантику at-least-once на уровне транспорта; идемпотентность на стороне consumer строится в notify-service через таблицу `processed_events` (§1.4.3). По сравнению с альтернативами семейства log-based platforms RabbitMQ потребляет меньше ресурсов и развёртывается в одном контейнере, что соответствует ограничениям одного VPS. Выбор RabbitMQ заменяет наблюдаемую у Settle Up зависимость от Firebase Cloud Messaging на self-hosted-аналог: события поступают в очередь брокера, а notify-service самостоятельно формирует in-app, web-push и email-сообщения, фиксируя факт доставки в `notification_deliveries` (§1.5.5).

**Клиентская часть: React, Vite, TanStack Query, Zustand.** Базовой клиентской библиотекой принят React 19 [14]. Выбор опирается на open-source реализацию expense-tracker-приложения уровня CoinKeeper, использующую React с TypeScript и Tailwind CSS [47], что показывает применимость связки в задаче учёта расходов; Splitwise также распространяется как React-подобное SPA [17, 42]. Сравнение с Vue.js в работе не проводится: рассмотренные аналоги используют либо React, либо Angular как часть платформы Firebase, и обоснование выбора между React и Vue не имеет опоры в архитектурах аналогов.

Управление состоянием разделено по природе данных: серверное состояние (запросы к backend, кеширование, инвалидация, фоновое обновление) изолировано в TanStack Query [35]; клиентское состояние, ограниченное контекстом аутентификации (access-токен в памяти, профиль пользователя), вынесено в Zustand [24]. Маршрутизация в data-режиме реализована через React Router [34]. Разделение сокращает класс ошибок, возникающих при смешении источников данных в едином хранилище.

Сборщиком клиентского приложения выбран Vite [36] с tree-shaking над нативными ESM-модулями и автоматическим code splitting на уровне динамических импортов: маршруты приложения выносятся в отдельные чанки, и первичный бандл не включает код экранов, недоступных без аутентификации. Режим рендеринга принят как SPA с клиентским рендерингом: всё прикладное содержимое расположено за аутентификацией (маршруты вида `/app/*`), публичных индексируемых страниц нет, требования SEO отсутствуют, поэтому серверный рендеринг добавил бы инфраструктурный слой без практической пользы. Этот выбор согласуется с практикой Splitwise и Settle Up, в которых веб-приложение также работает как клиентское SPA, обращающееся к внутреннему API.

**Инфраструктура: Nginx, Docker, единый VPS.** В качестве edge-сервера применяется Nginx [22] с асинхронной моделью обработки соединений. На уровне Nginx выполняются транспортные функции: TLS-терминация, маршрутизация запросов к frontend-приложению и api-gateway, очистка недоверенных заголовков `X-User-*`. Подробное распределение ответственности между Nginx, api-gateway и доменными сервисами рассматривается в §1.4.2.

Все компоненты упаковываются в Docker-контейнеры [11] и описываются в Docker Compose как единая топология с общими сетями и именованными томами для PostgreSQL и RabbitMQ; полный запуск системы на новом сервере сводится к одной команде при наличии установленного Docker. Этот подход инвертирует наблюдаемую у Splitwise (закрытая инфраструктура) и Settle Up (Firebase) зависимость от внешнего провайдера: размещение всех компонентов на одном VPS соответствует демонстрационному масштабу прототипа. Кластеризация PostgreSQL, разнесение сервисов на отдельные хосты и переход к оркестратору Kubernetes сохранены как направление развития v2 и не требуют изменений прикладного кода.

**Архитектурный подход.** Сервисное разбиение принято как минимально достаточное: пять backend-сервисов (auth-service, groups-service, expenses-service, expenses-worker, notify-service) и три инфраструктурных компонента (Nginx, api-gateway, frontend). Разбиение мотивировано не масштабом нагрузки, а академической задачей работы — продемонстрировать применимость событийной модели, паттерна Transactional Outbox [4, 7], идемпотентной обработки межсервисных событий и централизованной аутентификации через api-gateway [30]. Полное описание состава компонентов, контрактов событий и стратегии консистентности балансов (on-demand расчёт по ledger-таблицам с проектным решением read-through-кеша через `balance_snapshot` для v2) выполняется в §1.4.

### Выводы по подразделу 1.3.3

Принятый стек собран из решений, индустриальная применимость которых подтверждается архитектурами Splitwise (кеширование агрегатов поверх реляционной СУБД, SPA-клиент) и Settle Up (web-push как канал уведомлений), а также open-source реализациями expense-tracker-приложений с TypeScript-фронтендом на React. Отличие от рассмотренных продуктов сосредоточено в инфраструктурном выборе: вместо закрытой облачной инфраструктуры Splitwise и BaaS-платформы Firebase принят набор self-hosted-компонентов — PostgreSQL, RabbitMQ, Nginx — упакованных в Docker Compose, что устраняет выделенную в §1.2 зависимость от внешнего провайдера.

## Выводы по параграфу 1.3

Архитектурный анализ доступной части аналогов показал, что специализированные трекеры совместных расходов опираются на зрелые серверные стеки (Ruby on Rails у Splitwise, BaaS на базе Firebase у Settle Up) и предсказуемые клиентские решения (SPA у Splitwise, Angular у Settle Up), а отечественные приложения учёта личных финансов формируют вокруг себя экосистему открытых API (Дзен-мани) при сохранении закрытости серверной реализации. Tricount, Splid и встроенные банковские инструменты остаются за пределами архитектурного анализа в силу непубличности их технических деталей.

Принятый стек сочетает FastAPI на Python с PostgreSQL и RabbitMQ для серверной части, React 19 с Vite, TanStack Query и Zustand для клиентской части, Nginx и Docker Compose для инфраструктуры. Стек обоснован тремя группами аргументов: подтверждение применимости React и SPA-режима практикой Splitwise и Settle Up; устранение BaaS-зависимости заменой Firebase на собственный notify-service с web-push поверх RabbitMQ; пригодность Python и Pydantic для финансовой модели с фиксированной точкой и автоматически генерируемой спецификацией OpenAPI. Детальное проектирование архитектуры — состав компонентов, схема аутентификации, событийная модель и стратегия консистентности балансов — выполняется в §1.4 на основе принятого стека.
