# 1.6 Проектирование API и финансовой модели

Настоящий параграф посвящён описанию программного интерфейса разрабатываемой системы и формализации финансовой модели распределения расходов. Контракт взаимодействия клиента с backend-сервисами определяется посредством REST API, специфицированного в формате OpenAPI. Финансовая модель включает алгоритм вычисления долей при создании расхода, а также ledger-based алгоритм расчёта балансов, обеспечивающий корректный учёт всех транзакций в группе. Оба аспекта — интерфейсный и вычислительный — неразрывно связаны: структура API определяет входные данные алгоритмов, а алгоритмы задают семантику ответов.

## 1.6.1 Принципы проектирования API

Проектирование программного интерфейса системы опирается на архитектурный стиль REST, широко применяемый при проектировании программных интерфейсов веб-приложений [13]. Согласно данному подходу, ресурсы идентифицируются унифицированными URI, а взаимодействие осуществляется посредством стандартных методов протокола HTTP: `GET` для получения данных, `POST` для создания новых ресурсов или выполнения действий. Ответы содержат стандартные коды состояния HTTP, однозначно сигнализирующие об успехе или характере ошибки.

**Версионирование.** Все маршруты API включают явный версионный префикс `/api/v1/`. Данное решение обеспечивает обратную совместимость: при введении новой версии API клиенты, ориентированные на `/api/v1/`, продолжают работать без изменений. Версионирование через сегмент пути предпочтено версионированию через HTTP-заголовок как более очевидный и легко тестируемый способ [5].

**Спецификация OpenAPI и генерация схем.** Контракт API описывается в формате OpenAPI 3.1 [31]. В экосистеме FastAPI схемы генерируются автоматически из аннотаций типов Python и Pydantic-моделей, что исключает рассинхронизацию между кодом и документацией [13]. Спецификация доступна в режиме реального времени по эндпоинту `/docs` (Swagger UI) и `/openapi.json`. Каждая Pydantic-модель, описывающая тело запроса или ответа, одновременно является схемой валидации: некорректный запрос отклоняется до исполнения бизнес-логики.

**Идемпотентность мутирующих операций.** Создание расхода и запись погашения долга поддерживают заголовок `Idempotency-Key`. Ключ идемпотентности в совокупности с идентификатором пользователя-актора и хэшем тела запроса (SHA-256) образуют уникальный составной ключ. При повторном запросе с тем же ключом сервис возвращает код `200 OK` и кэшированный ответ вместо повторного создания ресурса. Механизм защищает от дублирования операций при сетевых сбоях и повторных отправках на стороне клиента [5].

**Передача идентификатора пользователя.** Механизм аутентификации через JWT RS256 и валидации на уровне api-gateway подробно описан в §1.4.2. На уровне контракта API это означает, что все защищённые эндпоинты получают идентификатор пользователя в заголовке `X-User-Id`, сформированном api-gateway после успешной валидации токена. Бизнес-сервисы доверяют этому заголовку и не выполняют повторной валидации JWT.

## 1.6.2 API сервиса аутентификации

Сервис аутентификации (`auth-service`) предоставляет шесть эндпоинтов, образующих полный цикл управления учётными записями и сессиями пользователей. Маршруты сгруппированы под префиксом `/api/v1/auth`.

**Таблица 1.3 — Эндпоинты сервиса аутентификации**

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | /api/v1/auth/register | Регистрация нового пользователя |
| POST | /api/v1/auth/login | Аутентификация и получение пары токенов |
| POST | /api/v1/auth/refresh | Ротация refresh-токена |
| POST | /api/v1/auth/logout | Отзыв refresh-токена |
| GET | /api/v1/auth/public-key | Получение публичного ключа RS256 в формате PEM |
| GET | /api/v1/auth/.well-known/jwks.json | JWKS-документ для проверки подписи JWT |

**Регистрация и аутентификация.** При обращении к `POST /register` сервис принимает адрес электронной почты и пароль, проверяет уникальность email, вычисляет хэш пароля по алгоритму bcrypt и создаёт запись пользователя в базе данных. При успешном завершении возвращается код `201 Created` с идентификатором пользователя. Эндпоинт `POST /login` принимает те же реквизиты, верифицирует пароль и при совпадении возвращает пару токенов: краткосрочный access-токен и долгосрочный refresh-токен.

**Схема токенов.** Access-токен представляет собой JWT, подписанный по алгоритму RS256 со временем жизни 15 минут. Полезная нагрузка токена включает `user_id`, адрес электронной почты и момент истечения срока действия. Refresh-токен является непрозрачной строкой (`ref_` + 24 случайных байта в кодировке base64) с временем жизни 30 дней. В базе данных хранится исключительно SHA-256 хэш refresh-токена, что предотвращает его компрометацию при утечке резервной копии.

**Ротация с детекцией компрометации.** Каждый refresh-токен принадлежит семейству (`token_family_id`). При обращении к `POST /refresh` сервис проверяет, является ли предъявленный токен актуальным (не отозванным) в пределах семейства. Если клиент предъявляет уже использованный токен того же семейства, это свидетельствует о возможной компрометации: все токены семейства немедленно аннулируются, что вынуждает пользователя пройти повторную аутентификацию [5]. Эндпоинт `POST /logout` отзывает предъявленный refresh-токен, не затрагивая остальные сессии пользователя.

**Публичный ключ и JWKS.** Эндпоинты `GET /public-key` и `GET /.well-known/jwks.json` предназначены для проверки подписи JWT на стороне API-шлюза. Публичный ключ возвращается в формате PEM; JWKS-документ предоставляет тот же ключ в стандартизированном формате JSON Web Key Set, что обеспечивает совместимость с внешними системами, поддерживающими автоматическое обнаружение ключей.

## 1.6.3 API сервиса групп

Сервис групп (`groups-service`) управляет жизненным циклом групп, членством в них и процедурой приглашения участников. Все операции требуют аутентификации, идентификатор пользователя извлекается из заголовка `X-User-Id`.

**Таблица 1.4 — Эндпоинты сервиса групп**

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | /api/v1/groups | Создание группы |
| GET | /api/v1/groups | Список групп текущего пользователя |
| POST | /api/v1/groups/{id}/members | Добавление участника в группу |
| GET | /api/v1/groups/{id}/members | Список участников группы |
| POST | /api/v1/groups/{id}/invitations | Создание приглашения по email |
| POST | /api/v1/groups/invitations/{id}/accept | Принятие приглашения |
| POST | /api/v1/groups/invitations/{id}/decline | Отклонение приглашения |

**Создание группы.** При вызове `POST /groups` сервис создаёт запись группы и одновременно добавляет инициатора в таблицу `memberships` с ролью `owner`. Данная операция атомарна: оба действия выполняются в одной транзакции базы данных. Ответ содержит идентификатор созданной группы и список текущих участников.

**Ролевая модель.** Членство в группе задаётся перечислимым атрибутом роли с тремя уровнями, образующими иерархию: `owner` > `admin` > `member`. Создатель группы всегда получает роль `owner`; права `admin` предоставляются владельцем. Добавление новых участников посредством `POST /groups/{id}/members` разрешено только пользователям с ролями `owner` или `admin`. Попытка участника с ролью `member` выполнить эту операцию завершается ответом `403 Forbidden`. Статус участия может принимать значения `active`, `left` (пользователь покинул группу самостоятельно) или `removed` (исключён администратором); к операциям с расходами допускаются только участники со статусом `active`.

**Система приглашений.** Эндпоинт `POST /groups/{id}/invitations` создаёт приглашение, адресованное указанному email-адресу. Приглашение допускает принятие или отклонение независимо от того, зарегистрирован ли адресат в системе на момент его создания. После принятия приглашения (`POST /invitations/{id}/accept`) сервис добавляет пользователя в группу с ролью `member`. Каждое приглашение имеет ограниченный срок действия; просроченные приглашения переходят в статус `expired` и не могут быть приняты.

## 1.6.4 API сервиса расходов

Сервис расходов (`expenses-service`) реализует финансовое ядро системы: создание расходов, запись погашений, получение текущих балансов и истории операций. Перечень эндпоинтов представлен в Таблице 1.5.

**Таблица 1.5 — Эндпоинты сервиса расходов**

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | /api/v1/expenses | Создание расхода |
| POST | /api/v1/expenses/settlements | Запись погашения долга |
| GET | /api/v1/expenses/{group_id}/balances | Текущие балансы участников группы |
| GET | /api/v1/expenses/{group_id}/history | Хронологический журнал операций группы |

**Создание расхода.** Запрос к `POST /expenses` содержит идентификатор группы, идентификатор плательщика, сумму расхода, код валюты, описание и список долей участников (`splits`). Каждый элемент списка задаёт пользователя и причитающуюся с него сумму. Сервис проверяет набор валидационных инвариантов (описанных в §1.6.7), после чего в рамках одной транзакции создаёт записи в таблицах `expenses`, `expense_splits` и `outbox`. Поддерживается заголовок `Idempotency-Key`.

**Запись погашения.** Эндпоинт `POST /expenses/settlements` фиксирует факт передачи денег от одного участника группы другому. Запрос включает идентификатор группы, идентификатор плательщика, идентификатор получателя и сумму. После прохождения валидации сервис записывает погашение в таблицу `settlements`, помечает кэшированный баланс как устаревший (`dirty = true`) и фиксирует событие в `outbox`. Эндпоинт также поддерживает идемпотентность.

**Балансы и история.** Эндпоинт `GET /{group_id}/balances` возвращает список текущих долгов в группе. Для каждой пары «должник — кредитор» указываются сумма долга и код валюты. Если флаг `dirty = true` для соответствующей записи `balance_snapshot`, сервис выполняет пересчёт inline перед возвратом ответа (стратегия read-through). Попарные задолженности вычисляются непосредственно из таблиц `expenses`, `expense_splits` и `settlements` алгоритмом, описанным в §1.6.5; таблица `balance_snapshot` кэширует результат этого вычисления — поле `dirty` служит индикатором актуальности кэша и сигнализирует о необходимости пересчёта. Эндпоинт `GET /{group_id}/history` предоставляет хронологический список всех расходов и погашений группы с поддержкой пагинации по курсору.

## 1.6.5 Финансовая модель и алгоритм расчёта балансов

### Представление денежных сумм

Ключевым техническим решением финансовой модели является хранение всех денежных значений в виде целочисленного поля `amount_minor` типа `bigint`, выражающего сумму в минимальных единицах валюты: копейках для рублей, центах для долларов и евро. Например, сумма 100,50 рублей представляется как `10050`. Данный подход принципиально исключает использование чисел с плавающей точкой (`float`, `double`) для хранения и передачи денежных значений, поскольку бинарное представление таких чисел не позволяет точно кодировать дробные десятичные значения [5].

Стоит пояснить соотношение этого решения с денежной моделью, описанной в §1.5. На уровне схемы базы данных суммы хранятся с типом `DECIMAL(NUMERIC(15, 2))` — для совместимости с SQL-агрегатными функциями и возможности прямых арифметических операций в PostgreSQL. На уровне API, однако, суммы передаются в поле `amount_minor` как целочисленные значения в минимальных единицах валюты: это позволяет клиенту оперировать исключительно целыми числами, не прибегая к десятичной арифметике на стороне JavaScript, где `0.1 + 0.2 ≠ 0.3`. Конвертация между представлениями выполняется на уровне сервиса при записи (`amount_minor / 100 → DECIMAL`) и при чтении (`DECIMAL × 100 → amount_minor`). Трёхбуквенный код валюты `currency_code` стандарта ISO 4217 фиксируется на уровне каждой операции, обеспечивая поддержку многовалютных групп.

### Модель расхода и алгоритм split engine

Каждый расход в системе описывается структурой с двумя обязательными элементами: плательщик (`paid_by_user_id`) и список долей (`splits`). Формально:

```
Expense {
    paid_by_user_id: UUID,
    amount_minor:    bigint,
    currency_code:   string,
    splits: [
        { user_id: UUID, amount_minor: bigint }
    ]
}
```
(1.4)

Центральным инвариантом модели расхода является условие нормировки долей:

$$\sum_{i=1}^{n} \text{splits}[i].\text{amount\_minor} = \text{expense.amount\_minor} \tag{1.5}$$

Данное условие проверяется перед записью расхода в базу данных; нарушение инварианта влечёт возврат ошибки `422 Unprocessable Entity` с описанием конкретного несоответствия.

Алгоритм split engine реализует два режима распределения суммы:

- **Равномерное распределение** (`equal`): сумма расхода $S$ делится поровну между $n$ участниками. Базовая доля составляет $\lfloor S / n \rfloor$. Остаток $S \bmod n$ (в минимальных единицах) прибавляется к доле первого участника в списке, что гарантирует выполнение инварианта формула (1.5) без округления.
- **Произвольное распределение** (`custom`): клиент передаёт явный список долей. Сервис проверяет выполнение инварианта формула (1.5) и принимает список без модификации.

Операция в целых числах (копейках) исключает ошибки округления, характерные для десятичного деления с остатком.

### Алгоритм расчёта балансов (ledger-based)

Балансы участников группы вычисляются по принципу бухгалтерского леджера: каждая зафиксированная операция трактуется как двусторонняя бухгалтерская запись. Алгоритм реализован в функции `_calculate_balances_from_records()` и выполняется в четыре последовательных шага.

**Шаг 1. Построение леджера из расходов.** Для каждого расхода и каждой его доли, если участник-должник не совпадает с плательщиком, в леджере формируется направленная запись вида «должник → кредитор»:

$$\text{ledger}[u_{\text{debtor}} \to u_{\text{creditor}},\ \text{currency}] \mathrel{+}= \text{split.amount\_minor} \tag{1.6}$$

Если плательщик сам является участником расхода (т. е. присутствует в списке долей), его собственная доля в леджер не включается: пользователь не может быть должником самому себе.

**Шаг 2. Применение погашений.** Для каждого зафиксированного погашения соответствующая запись леджера уменьшается на сумму платежа:

$$\text{ledger}[u_{\text{from}} \to u_{\text{to}},\ \text{currency}] \mathrel{-}= \text{settlement.amount\_minor} \tag{1.7}$$

**Шаг 3. Нормализация.** После применения всех погашений выполняются два действия. Во-первых, при наличии встречных записей для одной пары $(A \to B)$ и $(B \to A)$ производится взаимозачёт: меньшая сумма вычитается из большей, запись с меньшей суммой удаляется. Во-вторых, записи, принявшие отрицательное значение вследствие переплаты, инвертируются: запись $(u_i \to u_j, -x)$ преобразуется в $(u_j \to u_i, x)$. Записи с нулевым значением удаляются.

**Шаг 4. Сортировка.** Итоговый список долгов сортируется по должнику, кредитору и коду валюты для детерминированного представления в ответе API.

### Пример расчёта балансов

Рассмотрим группу из трёх участников: Алиса, Борис и Чарли. Приведём конкретный сценарий с числами (все суммы — в минимальных единицах валюты, рублях-копейках).

**Исходные операции:**

1. Алиса оплатила общий ужин на 1 000,00 рублей (`10000` коп.). Расход поделён: Борис — `6000` коп. (60,00 руб.), Чарли — `4000` коп. (40,00 руб.).
2. Борис оплатил такси на 450,00 рублей (`4500` коп.). Расход поделён поровну: Алиса — `1500` коп., Чарли — `1500` коп., Борис — `1500` коп. (собственная доля Бориса в леджер не включается).

**Шаг 1 — построение леджера из расходов:**

Из расхода 1:
- $\text{ledger}[\text{Борис} \to \text{Алиса},\ \text{RUB}] = 6000$
- $\text{ledger}[\text{Чарли} \to \text{Алиса},\ \text{RUB}] = 4000$

Из расхода 2:
- $\text{ledger}[\text{Алиса} \to \text{Борис},\ \text{RUB}] = 1500$
- $\text{ledger}[\text{Чарли} \to \text{Борис},\ \text{RUB}] = 1500$

**Состояние леджера перед погашениями** (Таблица 1.6):

**Таблица 1.6 — Состояние леджера после регистрации расходов**

| Должник | Кредитор | Валюта | Сумма (коп.) | Сумма (руб.) |
|---------|----------|--------|-------------|--------------|
| Борис | Алиса | RUB | 6 000 | 60,00 |
| Алиса | Борис | RUB | 1 500 | 15,00 |
| Чарли | Алиса | RUB | 4 000 | 40,00 |
| Чарли | Борис | RUB | 1 500 | 15,00 |

**Шаг 2 — применение погашений.** Борис переводит Алисе 3 000 коп.:
- $\text{ledger}[\text{Борис} \to \text{Алиса}] = 6000 - 3000 = 3000$

**Шаг 3 — нормализация.** В леджере имеются встречные записи для пары Борис–Алиса: $\text{ledger}[\text{Борис} \to \text{Алиса}] = 3000$ и $\text{ledger}[\text{Алиса} \to \text{Борис}] = 1500$. Выполняется взаимозачёт: $\text{ledger}[\text{Борис} \to \text{Алиса}] = 3000 - 1500 = 1500$, запись $\text{ledger}[\text{Алиса} \to \text{Борис}]$ удаляется. Прочих отрицательных записей нет.

**Итоговые балансы:**

- Борис должен Алисе: 1 500 коп. (15,00 руб.)
- Чарли должен Алисе: 4 000 коп. (40,00 руб.)
- Чарли должен Борису: 1 500 коп. (15,00 руб.)

Данный пример демонстрирует, что алгоритм сохраняет все попарные задолженности и выполняет взаимозачёт встречных записей. Однако число попарных долгов в группе из $N$ участников может достигать $N(N-1)/2$. Задача сведения этого множества к минимальному числу транзакций решается отдельным алгоритмом, описанным в §1.6.6.

## 1.6.6 Алгоритм минимизации взаиморасчётов

### Постановка задачи

После выполнения алгоритма расчёта балансов (§1.6.5) леджер может содержать до $N(N-1)/2$ попарных записей долгов для $N$ участников группы. Прямая интерпретация этих записей как обязательных транзакций нерациональна: значительная часть долгов может быть погашена транзитно. Задача сведения произвольного долгового графа к минимальному числу переводов установлена как NP-трудная в общем случае [7]; для практических целей применяется жадный алгоритм, обеспечивающий число транзакций не более $N-1$.

### Жадный алгоритм упрощения долгового графа

Алгоритм выполняется в три шага.

**Шаг 1. Вычисление сальдо.** Для каждого участника вычисляется чистое сальдо: сумма всех входящих долгов (участник является кредитором) за вычетом суммы всех исходящих долгов (участник является должником). Участник с положительным сальдо — кредитор, с отрицательным — должник, с нулевым — в расчёте не участвует.

**Шаг 2. Сортировка.** Кредиторы упорядочиваются по убыванию сальдо (наибольший кредитор — первый), должники — по убыванию абсолютного значения долга (наибольший должник — первый).

**Шаг 3. Жадное сопоставление.** Итеративно: наибольший должник переводит максимально возможную сумму наибольшему кредитору. Переводимая сумма равна минимуму из абсолютного значения долга должника и сальдо кредитора. После каждого шага обновляются сальдо обоих участников; участники с нулевым сальдо исключаются из дальнейшего рассмотрения. Итерации продолжаются до полного обнуления всех сальдо.

### Гарантия эффективности

Каждая итерация алгоритма обнуляет сальдо хотя бы одного участника, поэтому число транзакций не превышает $N-1$ вне зависимости от исходной конфигурации долгов. Тогда как попарное представление могло бы потребовать до $N(N-1)/2$ переводов, жадный алгоритм гарантирует линейную по числу участников сложность результата.

### Пример

Рассмотрим группу из трёх участников с итоговыми балансами из §1.6.5: Борис должен Алисе 1 500 коп., Чарли должен Алисе 4 000 коп., Чарли должен Борису 1 500 коп. Сальдо: Алиса = +5 500 коп., Борис = 0 коп. (после взаимозачёта он кредитор Чарли на 1 500 и должник Алисе на 1 500), Чарли = −5 500 коп. В данном случае жадный алгоритм сводит расчёты к двум транзакциям: Чарли переводит Алисе 4 000 коп. и Борису 1 500 коп., — вместо трёх попарных операций.

Аналогичный подход к упрощению долгового графа применяется в сервисе Splitwise [14] и описан в работе [3].

## 1.6.7 Валидационные инварианты API

В отличие от инвариантов на уровне СУБД, описанных в §1.5.6, API-уровень обеспечивает проверки бизнес-логики до обращения к базе данных, выступая первым рубежом валидации.

Корректность операций обеспечивается двухуровневой системой проверок: Pydantic-схемы осуществляют структурную валидацию на границе HTTP-запроса, тогда как бизнес-инварианты проверяются внутри транзакции базы данных.

**Инварианты создания расхода:**

- сумма долей участников равна полной сумме расхода: $\sum \text{splits[i].amount\_minor} = \text{amount\_minor}$ — нарушение возвращает `422`;
- плательщик является активным участником группы (`status = active`);
- все пользователи из списка долей являются активными участниками группы;
- пользователь-актор (из заголовка `X-User-Id`) является активным участником группы;
- `amount_minor > 0` — нулевые и отрицательные суммы недопустимы;
- список долей не пуст и содержит не менее одного элемента.

**Инварианты создания погашения:**

- `from_user_id ≠ to_user_id` — пользователь не может погашать долг самому себе;
- оба участника (`from_user_id` и `to_user_id`) являются активными членами группы;
- актор является одним из участников операции (`from_user_id = X-User-Id`);
- `amount_minor ≤ текущий_долг(from → to, currency)` — запрещено «переплачивать» сверх зафиксированного долга; данный инвариант проверяется на уровне API при создании погашения, тогда как Шаг 3 алгоритма нормализации (§1.6.5) обеспечивает корректность для исторических данных и случаев параллельного создания расходов и погашений, когда состояние леджера может измениться между проверкой инварианта и пересчётом балансов;
- `amount_minor > 0`.

При нарушении любого из перечисленных инвариантов сервис возвращает ответ с кодом `422 Unprocessable Entity` и структурированным описанием ошибки, включающим поле-нарушитель и человекочитаемое сообщение. Ответы об ошибках форматируются единообразно для всех сервисов, что упрощает обработку ошибок на стороне клиента.

Таким образом, в параграфе 1.6 спроектирован программный интерфейс системы и описана финансовая модель. REST API организован по принципу версионирования маршрутов и генерации OpenAPI-спецификации из типизированного кода, что обеспечивает актуальность документации без ручного сопровождения. Семнадцать эндпоинтов трёх сервисов охватывают полный операционный цикл: управление учётными записями и токенами, работу с группами и приглашениями, создание расходов и погашение долгов. Финансовая модель строится на целочисленном представлении денежных сумм в минимальных единицах валюты, что исключает погрешности, присущие вычислениям с плавающей точкой. Ledger-based алгоритм расчёта балансов корректно учитывает историю всех расходов и погашений, вычисляя попарные задолженности участников; жадный алгоритм минимизации взаиморасчётов (§1.6.6) сводит число необходимых транзакций к величине, не превышающей $N-1$. Двухуровневая система валидационных инвариантов — структурная на уровне Pydantic и транзакционная на уровне базы данных — обеспечивает целостность финансовых данных. В главе 2 рассматривается реализация описанных спецификаций в программном коде backend-сервисов и frontend-приложения.
