# 1.6 Проектирование API и финансовой модели

Программный интерфейс разрабатываемой системы определяется контрактом REST API, специфицированным в формате OpenAPI. Финансовая модель включает алгоритм вычисления долей при создании расхода, а также ledger-based алгоритм расчёта балансов, обеспечивающий корректный учёт всех транзакций в группе. Оба аспекта — интерфейсный и вычислительный — неразрывно связаны: структура API определяет входные данные алгоритмов, а алгоритмы задают семантику ответов.

## 1.6.1 Принципы проектирования API

Проектирование программного интерфейса системы опирается на архитектурный стиль REST, широко применяемый при проектировании программных интерфейсов веб-приложений [13]. Согласно данному подходу, ресурсы идентифицируются унифицированными URI, а взаимодействие осуществляется посредством стандартных методов протокола HTTP: `GET` для получения данных, `POST` для создания новых ресурсов или выполнения действий, `PATCH` для частичного обновления существующих ресурсов, `DELETE` для их удаления. Ответы содержат стандартные коды состояния HTTP, однозначно сигнализирующие об успехе или характере ошибки.

**Версионирование.** Все маршруты API включают явный версионный префикс `/api/v1/`. Данное решение обеспечивает обратную совместимость: при введении новой версии API клиенты, ориентированные на `/api/v1/`, продолжают работать без изменений. Версионирование через сегмент пути предпочтено версионированию через HTTP-заголовок как более очевидный и легко тестируемый способ [13].

**Спецификация OpenAPI и генерация схем.** Контракт API описывается в формате OpenAPI 3.1 [31]. В экосистеме FastAPI схемы генерируются автоматически из аннотаций типов Python и Pydantic-моделей, что исключает рассинхронизацию между кодом и документацией [13]. Спецификация доступна в режиме реального времени по эндпоинту `/docs` (Swagger UI) и `/openapi.json`. Каждая Pydantic-модель, описывающая тело запроса или ответа, одновременно является схемой валидации: некорректный запрос отклоняется до исполнения бизнес-логики.

**Идемпотентность мутирующих операций.** Создание расхода и запись погашения долга поддерживают заголовок `Idempotency-Key`. Составной первичный ключ таблицы `expenses.idempotency_keys` образует тройка `(idempotency_key, operation_scope, actor_user_id)`: имя операции (`operation_scope`) исключает коллизии между ключами от разных типов мутирующих эндпоинтов одного и того же пользователя. Дополнительно сохраняется SHA-256-хэш тела запроса (`request_hash`): он применяется для распознавания повторной отправки с тем же ключом, но другим телом — такой случай трактуется как ошибка клиента и возвращает `409 Conflict`. При корректном повторе с прежними ключом и телом сервис возвращает код `200 OK` и кэшированный ответ исходной операции вместо повторного выполнения бизнес-логики. Механизм защищает от дублирования операций при сетевых сбоях и повторных отправках на стороне клиента [5].

**Передача идентификатора пользователя.** Механизм аутентификации через JWT RS256 и валидации на уровне api-gateway подробно описан в §1.4.2. На уровне контракта API это означает, что все защищённые эндпоинты получают идентификатор пользователя в заголовке `X-User-Id`, сформированном api-gateway после успешной валидации токена. Бизнес-сервисы доверяют этому заголовку и не выполняют повторной валидации JWT.

## 1.6.2 API сервиса аутентификации

Сервис аутентификации (`auth-service`) предоставляет семь эндпоинтов, образующих полный цикл управления учётными записями и сессиями пользователей. Маршруты сгруппированы под префиксом `/api/v1/auth`.

**Таблица 1.4 — Эндпоинты сервиса аутентификации**

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | /api/v1/auth/register | Регистрация нового пользователя |
| POST | /api/v1/auth/login | Аутентификация и выдача access-токена |
| POST | /api/v1/auth/refresh | Ротация refresh-токена |
| POST | /api/v1/auth/logout | Отзыв refresh-токена текущей сессии |
| GET | /api/v1/auth/me | Получение профиля текущего пользователя |
| GET | /api/v1/auth/public-key | Получение публичного ключа RS256 в формате PEM |
| GET | /api/v1/auth/.well-known/jwks.json | JWKS-документ для проверки подписи JWT |

**Регистрация и аутентификация.** При обращении к `POST /register` сервис принимает адрес электронной почты, отображаемое имя (`display_name` длиной от одного до 80 символов) и пароль, проверяет уникальность email, вычисляет хэш пароля по алгоритму Argon2 [40] и создаёт запись пользователя в базе данных. При успешном завершении возвращается код `201 Created` с телом, содержащим `id`, `email` и `display_name` — тот же набор полей возвращает эндпоинт `GET /me`, предназначенный для отображения профиля в клиентском приложении. Эндпоинт `POST /login` принимает учётные реквизиты, верифицирует пароль и при совпадении формирует пару токенов: краткосрочный access-токен возвращается в теле ответа, долгосрочный refresh-токен устанавливается в HTTP-only Secure Cookie с атрибутом `SameSite=Strict`. Размещение refresh-токена в cookie, недоступной JavaScript-коду, предотвращает его извлечение через XSS-уязвимости [40]; на эндпоинте `POST /refresh` сервис читает значение cookie и проводит ротацию по описанной ниже схеме без необходимости передавать refresh-токен в теле запроса.

**Схема токенов.** Access-токен представляет собой JWT, подписанный по алгоритму RS256 со временем жизни 15 минут. Полезная нагрузка токена соответствует стандартному набору claims по RFC 7519 [39]: `sub` (идентификатор пользователя), `iss` (издатель), `aud` (получатель), `iat`/`nbf`/`exp` (временны́е метки выпуска, начала действия и истечения срока), `jti` (уникальный идентификатор токена, используемый для детектирования повторного использования). Адрес электронной почты в claims не включается; backend-сервисы при необходимости получают его через выделенный API auth-сервиса. Refresh-токен является непрозрачной строкой (`ref_` + 24 случайных байта в кодировке base64) с временем жизни 30 дней. В базе данных хранится исключительно SHA-256 хэш refresh-токена, что предотвращает его компрометацию при утечке резервной копии.

**Ротация с детекцией компрометации.** Каждый refresh-токен принадлежит семейству (`token_family_id`). При обращении к `POST /refresh` сервис проверяет, является ли предъявленный токен актуальным (не отозванным) в пределах семейства. Если клиент предъявляет уже использованный токен того же семейства, это свидетельствует о возможной компрометации: все токены семейства немедленно аннулируются, что вынуждает пользователя пройти повторную аутентификацию [5]. Эндпоинт `POST /logout` отзывает предъявленный refresh-токен, не затрагивая остальные сессии пользователя.

**Публичный ключ и JWKS.** Эндпоинты `GET /public-key` и `GET /.well-known/jwks.json` предназначены для проверки подписи JWT на стороне API-шлюза. Публичный ключ возвращается в формате PEM; JWKS-документ предоставляет тот же ключ в стандартизированном формате JSON Web Key Set, что обеспечивает совместимость с внешними системами, поддерживающими автоматическое обнаружение ключей.

## 1.6.3 API сервиса групп

Сервис групп (`groups-service`) управляет жизненным циклом групп, членством в них и процедурой приглашения участников. Все операции требуют аутентификации, идентификатор пользователя извлекается из заголовка `X-User-Id`.

**Таблица 1.5 — Эндпоинты сервиса групп**

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | /api/v1/groups | Создание группы |
| GET | /api/v1/groups | Список групп текущего пользователя |
| PATCH | /api/v1/groups/{group_id} | Изменение наименования и валюты группы |
| POST | /api/v1/groups/{group_id}/archive | Перевод группы в архивный режим (read-only) |
| GET | /api/v1/groups/{group_id}/members | Список участников группы |
| POST | /api/v1/groups/{group_id}/members | Добавление участника в группу |
| DELETE | /api/v1/groups/{group_id}/members/{user_id} | Исключение участника из группы |
| PATCH | /api/v1/groups/{group_id}/members/{user_id}/role | Изменение роли участника группы |
| POST | /api/v1/groups/{group_id}/leave | Выход пользователя из группы по собственной инициативе |
| GET | /api/v1/groups/{group_id}/invitations | Список приглашений группы |
| POST | /api/v1/groups/{group_id}/invitations | Создание приглашения зарегистрированному пользователю (по `target_user_id`) |
| POST | /api/v1/groups/invitations/{id}/accept | Принятие приглашения |
| POST | /api/v1/groups/invitations/{id}/decline | Отклонение приглашения |
| POST | /api/v1/groups/invitations/{id}/revoke | Отзыв ранее созданного приглашения |

**Создание группы.** При вызове `POST /groups` сервис создаёт запись группы и одновременно добавляет инициатора в таблицу `memberships` с ролью `owner`. Данная операция атомарна: оба действия выполняются в одной транзакции базы данных. Ответ содержит идентификатор созданной группы и список текущих участников.

**Ролевая модель.** Членство в группе задаётся перечислимым атрибутом роли с тремя уровнями, образующими иерархию: `owner` > `admin` > `member`. Создатель группы всегда получает роль `owner`; права `admin` предоставляются владельцем. Добавление новых участников посредством `POST /groups/{id}/members` разрешено только пользователям с ролями `owner` или `admin`. Попытка участника с ролью `member` выполнить эту операцию завершается ответом `403 Forbidden`. Статус участия может принимать значения `active`, `left` (пользователь покинул группу самостоятельно) или `removed` (исключён администратором); к операциям с расходами допускаются только участники со статусом `active`.

**Операции управления группой.** Помимо создания и просмотра, сервис предоставляет полный набор административных действий над существующей группой. Эндпоинт `PATCH /groups/{group_id}` позволяет владельцу изменить наименование и валюту по умолчанию; `POST /groups/{group_id}/archive` переводит группу в архивный режим, в котором запрещены любые мутирующие операции с расходами при сохранении исторических данных. Изменение состава участников осуществляется операциями `DELETE /groups/{group_id}/members/{user_id}` (исключение администратором) и `POST /groups/{group_id}/leave` (выход по собственной инициативе); смена роли реализована эндпоинтом `PATCH /groups/{group_id}/members/{user_id}/role`. Авторизация всех перечисленных операций опирается на ролевую иерархию, описанную выше: попытка выполнения недоступного действия завершается ответом `403 Forbidden`.

**Система приглашений.** Эндпоинт `POST /groups/{group_id}/invitations` создаёт приглашение, адресованное зарегистрированному пользователю системы (поле `target_user_id`). После принятия приглашения (`POST /invitations/{id}/accept`) сервис добавляет пользователя в группу с ролью `member`. Создатель приглашения вправе отозвать его до момента принятия или отклонения операцией `POST /invitations/{id}/revoke`; владельцы и администраторы могут просматривать актуальный список приглашений через `GET /groups/{group_id}/invitations`. Каждое приглашение имеет ограниченный срок действия, определяемый полем `expires_at`; по его истечении приглашение не может быть принято. Поддержка email-приглашений с автогенерацией одноразового токена (для отправки приглашений по адресу не зарегистрированных в системе пользователей) предусмотрена как направление развития v2 и в текущей версии не реализована.

## 1.6.4 API сервиса расходов

Сервис расходов (`expenses-service`) реализует финансовое ядро системы: создание расходов, запись погашений, получение текущих балансов и истории операций. Перечень эндпоинтов представлен в Таблице 1.6.

**Таблица 1.6 — Эндпоинты сервиса расходов**

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | /api/v1/expenses | Создание расхода |
| GET | /api/v1/expenses/{expense_id} | Получение расхода с детализацией долей участников |
| PATCH | /api/v1/expenses/{expense_id} | Редактирование расхода |
| DELETE | /api/v1/expenses/{expense_id} | Удаление расхода |
| POST | /api/v1/expenses/settlements | Запись погашения долга |
| GET | /api/v1/expenses/{group_id}/balances | Текущие балансы участников группы |
| GET | /api/v1/expenses/{group_id}/balances/simplified | Минимизированный список переводов (не более N−1) |
| GET | /api/v1/expenses/{group_id}/history | Хронологический журнал операций группы |

**Создание расхода.** Запрос к `POST /expenses` содержит идентификатор группы, идентификатор плательщика, сумму расхода, код валюты, описание и список долей участников (`splits`). Каждый элемент списка задаёт пользователя и причитающуюся с него сумму. Сервис проверяет набор валидационных инвариантов (описанных в §1.6.7), после чего в рамках одной транзакции создаёт записи в таблицах `expenses`, `expense_splits` и `outbox`. Поддерживается заголовок `Idempotency-Key`.

**Просмотр и редактирование расхода.** Эндпоинт `GET /expenses/{expense_id}` возвращает детализированное представление расхода вместе со списком долей участников и используется клиентским приложением при открытии экрана расхода и формы редактирования. Эндпоинт `PATCH /expenses/{expense_id}` позволяет внести изменения в существующий расход: при одновременной корректировке полной суммы и распределения долей проверка инварианта формула (1.4) выполняется на этапе структурной валидации запроса, что описано в §1.6.7. Эндпоинт `DELETE /expenses/{expense_id}` удаляет расход: запись из таблицы `expenses` удаляется, связанные строки таблицы `expense_splits` исключаются каскадно по внешнему ключу. Снимок удалённой сущности — сумма, валюта, плательщик и состав долей — фиксируется в `activity_log` в той же транзакции, что обеспечивает реконструкцию контекста при последующем аудите. Все мутирующие операции порождают соответствующие события в `outbox` (§1.5.4) в одной транзакции с изменением доменных таблиц.

**Запись погашения.** Эндпоинт `POST /expenses/settlements` фиксирует факт передачи денег от одного участника группы другому. Запрос включает идентификатор группы, идентификатор плательщика, идентификатор получателя и сумму. После прохождения валидации сервис записывает погашение в таблицу `settlements` и фиксирует событие в `outbox`. Эндпоинт также поддерживает идемпотентность.

**Балансы и история.** Эндпоинт `GET /{group_id}/balances` возвращает список текущих долгов в группе. Для каждой пары «должник — кредитор» указываются сумма долга и код валюты. Попарные задолженности вычисляются алгоритмом §1.6.5 непосредственно из таблиц `expenses`, `expense_splits` и `settlements`; стратегия кэширования агрегированных балансов (v1 on-demand, v2 `balance_snapshot`) рассматривается в §1.4.4. Дополнительно доступен эндпоинт `GET /{group_id}/balances/simplified`, возвращающий упрощённый список переводов длиной не более N−1 (где N — число участников с ненулевым балансом); алгоритм подробно описан в §1.6.6. Эндпоинт `GET /{group_id}/history` предоставляет хронологический список всех расходов и погашений группы с offset-based пагинацией: запрос принимает параметры `limit` (размер страницы) и `offset` (смещение от начала); ответ помимо самой страницы содержит поле `next_offset`, использование которого позволяет последовательно получать следующие страницы. Курсорная пагинация по составному ключу `(created_at, id)` рассматривается как направление развития v2 при росте объёма истории и числа конкурентных операций; в актуальной реализации offset-схема обеспечивает достаточную для сценариев групп малого и среднего размера производительность.

## 1.6.5 Финансовая модель и алгоритм расчёта балансов

### Представление денежных сумм

API наследует денежную модель, зафиксированную в §1.5.4: все суммы передаются в поле `amount_minor` как целое число в минимальных единицах валюты (копейки для RUB, центы для USD/EUR). Использование типа с плавающей точкой недопустимо ввиду накопления ошибок округления [5]. На уровне API это означает, что поле `amount_minor` сериализуется в JSON как обычное целое число без промежуточных конвертаций; преобразование в десятичную форму (например, `1234.56`) выполняется исключительно на клиенте при отображении пользователю. Трёхбуквенный код валюты `currency_code` стандарта ISO 4217 фиксируется на уровне каждой операции, обеспечивая поддержку многовалютных групп.

### Модель расхода и алгоритм split engine

Каждый расход в системе описывается совокупностью полей, состав которых приведён в Таблице 1.7.

**Таблица 1.7 — Поля доменной модели расхода**

| Поле | Тип | Описание |
|------|-----|----------|
| `paid_by_user_id` | UUID | Идентификатор пользователя, фактически оплатившего расход |
| `amount_minor` | bigint | Полная сумма расхода в минимальных единицах валюты |
| `currency_code` | string (ISO 4217) | Трёхбуквенный код валюты расхода |
| `splits[i].user_id` | UUID | Идентификатор участника, на которого относится доля |
| `splits[i].amount_minor` | bigint | Доля участника в минимальных единицах валюты |

Центральным инвариантом модели расхода является условие нормировки долей:

$$\sum_{i=1}^{n} \text{splits}[i].\text{amount\_minor} = \text{expense.amount\_minor} \tag{1.4}$$

Данное условие проверяется перед записью расхода в базу данных; нарушение инварианта влечёт возврат ошибки `400 Bad Request` с описанием конкретного несоответствия.

Алгоритм split engine реализован на стороне клиентского приложения в составе модуля `frontend/app/utils/money.ts` и поддерживает два режима распределения суммы:

- **Равномерное распределение** (`equal`): сумма расхода $S$ делится поровну между $n$ участниками. Базовая доля составляет $\lfloor S / n \rfloor$. Остаток $S \bmod n$ (в минимальных единицах) прибавляется к доле плательщика, что гарантирует выполнение инварианта формула (1.4) без округления.
- **Произвольное распределение** (`custom`): пользователь задаёт каждую долю вручную; клиент при отправке проверяет соответствие суммы долей сумме расхода и блокирует отправку при нарушении инварианта.

В обоих режимах REST API принимает уже готовый список `splits` и не выполняет повторного формирования долей: серверная часть отвечает исключительно за проверку инварианта формула (1.4) до записи в базу данных. Принятое разделение ответственности сохраняет за сервером роль авторитетного арбитра финансовой корректности, при этом интерактивный пересчёт долей в форме создания расхода выполняется без сетевого обмена. Операции в целых числах (минимальных единицах валюты) исключают ошибки округления, характерные для десятичного деления с остатком, как на стороне клиента, так и на стороне сервера. Режим формирования каждой доли сохраняется в поле `expense_splits.split_type` (см. §1.5.4) и используется при отображении истории.

### Алгоритм расчёта балансов (ledger-based)

Балансы участников группы вычисляются по принципу бухгалтерского леджера: каждая зафиксированная операция трактуется как двусторонняя бухгалтерская запись. Алгоритм реализован в функции `_calculate_balances_from_records()` и выполняется в четыре последовательных шага.

**Шаг 1. Построение леджера из расходов.** Для каждого расхода и каждой его доли, если участник-должник не совпадает с плательщиком, в леджере формируется направленная запись вида «должник → кредитор»:

$$\text{ledger}[u_{\text{debtor}} \to u_{\text{creditor}},\ \text{currency}] \mathrel{+}= \text{split.amount\_minor} \tag{1.5}$$

Если плательщик сам является участником расхода (т. е. присутствует в списке долей), его собственная доля в леджер не включается: пользователь не может быть должником самому себе.

**Шаг 2. Применение погашений.** Для каждого зафиксированного погашения соответствующая запись леджера уменьшается на сумму платежа:

$$\text{ledger}[u_{\text{from}} \to u_{\text{to}},\ \text{currency}] \mathrel{-}= \text{settlement.amount\_minor} \tag{1.6}$$

**Шаг 3. Нормализация.** После применения всех погашений выполняются два действия. Во-первых, при наличии встречных записей для одной пары $(A \to B)$ и $(B \to A)$ производится взаимозачёт: меньшая сумма вычитается из большей, запись с меньшей суммой удаляется. Во-вторых, записи, принявшие отрицательное значение вследствие переплаты, инвертируются: запись $(u_i \to u_j, -x)$ преобразуется в $(u_j \to u_i, x)$. Записи с нулевым значением удаляются.

**Шаг 4. Сортировка.** Итоговый список долгов сортируется по должнику, кредитору и коду валюты для детерминированного представления в ответе API.

### Пример расчёта балансов

Рассмотрим группу из трёх участников: Алиса, Борис и Чарли. Приведём конкретный сценарий с числами (все суммы — в минимальных единицах валюты, рублях-копейках).

**Исходные операции:**

1. Алиса оплатила общий ужин на 1 000,00 рублей (`10000` коп.). Расход поделён: Борис — `6000` коп. (60,00 руб.), Чарли — `4000` коп. (40,00 руб.).
2. Борис оплатил такси на 450,00 рублей (`4500` коп.). Расход поделён поровну: Алиса — `1500` коп., Чарли — `1500` коп., Борис — `1500` коп. (собственная доля Бориса в леджер не включается).

**Шаг 1 — построение леджера из расходов:**

Из расхода 1:
- $\text{ledger}[\text{Борис} \to \text{Алиса},\ \text{RUB}] = 6000$
- $\text{ledger}[\text{Чарли} \to \text{Алиса},\ \text{RUB}] = 4000$

Из расхода 2:
- $\text{ledger}[\text{Алиса} \to \text{Борис},\ \text{RUB}] = 1500$
- $\text{ledger}[\text{Чарли} \to \text{Борис},\ \text{RUB}] = 1500$

**Состояние леджера перед погашениями** (Таблица 1.8):

**Таблица 1.8 — Состояние леджера после регистрации расходов**

| Должник | Кредитор | Валюта | Сумма (коп.) | Сумма (руб.) |
|---------|----------|--------|-------------|--------------|
| Борис | Алиса | RUB | 6 000 | 60,00 |
| Алиса | Борис | RUB | 1 500 | 15,00 |
| Чарли | Алиса | RUB | 4 000 | 40,00 |
| Чарли | Борис | RUB | 1 500 | 15,00 |

**Шаг 2 — применение погашений.** Борис переводит Алисе 3 000 коп.:
- $\text{ledger}[\text{Борис} \to \text{Алиса}] = 6000 - 3000 = 3000$

**Шаг 3 — нормализация.** В леджере имеются встречные записи для пары Борис–Алиса: $\text{ledger}[\text{Борис} \to \text{Алиса}] = 3000$ и $\text{ledger}[\text{Алиса} \to \text{Борис}] = 1500$. Выполняется взаимозачёт: $\text{ledger}[\text{Борис} \to \text{Алиса}] = 3000 - 1500 = 1500$, запись $\text{ledger}[\text{Алиса} \to \text{Борис}]$ удаляется. Прочих отрицательных записей нет.

**Итоговые балансы:**

- Борис должен Алисе: 1 500 коп. (15,00 руб.)
- Чарли должен Алисе: 4 000 коп. (40,00 руб.)
- Чарли должен Борису: 1 500 коп. (15,00 руб.)

Данный пример демонстрирует, что алгоритм сохраняет все попарные задолженности и выполняет взаимозачёт встречных записей. Однако число попарных долгов в группе из $N$ участников может достигать $N(N-1)/2$. Задача сокращения числа транзакций решается отдельным алгоритмом, описанным в §1.6.6 (точная минимизация NP-трудна, применяется жадная эвристика с границей не более N−1).

## 1.6.6 Алгоритм упрощения взаиморасчётов

### Постановка задачи

После выполнения алгоритма расчёта балансов (§1.6.5) леджер может содержать до $N(N-1)/2$ попарных записей долгов для $N$ участников группы. Прямая интерпретация этих записей как обязательных транзакций нерациональна: значительная часть долгов может быть погашена транзитно. Задача сведения произвольного долгового графа к минимальному числу переводов установлена как NP-трудная в общем случае [7]; для практических целей применяется жадный алгоритм, обеспечивающий число транзакций не более $N-1$.

Система предоставляет два согласованных представления одного и того же состояния расчётов. Попарное нормализованное представление (§1.6.5, эндпоинт `GET /balances`) сохраняет структуру «кто, кому и за что должен» и максимизирует прозрачность долгов. Упрощённое представление (эндпоинт `GET /balances/simplified`) переходит от попарных долгов к вектору нетто-сальдо и сокращает урегулирование до не более $N-1$ перевода, облегчая погашение. Оба представления исходят из одного леджера и согласованы инвариантом, вводимым ниже (формула 1.8); выбор между ними остаётся за пользователем.

### Нетто-сальдо и инвариант сохранения

Попарный леджер (§1.6.5) эквивалентен агрегированному представлению — вектору нетто-сальдо участников. Нетто-сальдо $b_{\text{cur}}(u)$ участника $u$ в валюте cur определяется как

$$b_{\text{cur}}(u) = P(u) - C(u) + S_{\text{out}}(u) - S_{\text{in}}(u), \tag{1.7}$$

где $P(u)$ — сумма расходов, оплаченных участником ($e.\text{paid\_by}=u$); $C(u)$ — сумма всех начисленных ему долей ($\text{splits}[i].\text{user\_id}=u$, включая собственную долю в оплаченных им расходах); $S_{\text{out}}(u)$ и $S_{\text{in}}(u)$ — суммы отправленных ($s.\text{from}=u$) и полученных ($s.\text{to}=u$) погашений; все величины выражены в `amount_minor` и ограничены валютой cur. Положительное $b_{\text{cur}}(u)$ означает, что группа должна участнику, отрицательное — что должен он. Связь с леджером: $b_{\text{cur}}(u)$ равно сумме входящих записей (где $u$ — кредитор) за вычетом исходящих (где $u$ — должник).

Для каждой валюты выполняется инвариант сохранения сальдо:

$$\sum_{u} b_{\text{cur}}(u) = 0. \tag{1.8}$$

Инвариант выполняется покомпонентно по валютам. В каждом расходе сумма всех долей равна сумме расхода (формула 1.4), причём суммирование охватывает и собственную долю плательщика; поэтому при суммировании (1.7) по всем участникам $\sum_u P(u)$ сокращается с $\sum_u C(u)$, а каждое погашение переносит равную величину между отправителем и получателем, давая $\sum_u S_{\text{out}}(u) = \sum_u S_{\text{in}}(u)$. Суммарное сальдо группы по каждой валюте тождественно равно нулю.

Нетто-сальдо инвариантно относительно нормализации леджера (Шаг 3, §1.6.5): взаимозачёт встречных рёбер не меняет разности входящих и исходящих сумм. Поэтому значение, вычисленное по формуле (1.7) из исходных операций, совпадает с сальдо, вычисленным из нормализованного леджера, и используется далее в жадном алгоритме.

### Жадный алгоритм упрощения долгового графа

Алгоритм выполняется в три шага. В мультивалютной группе шаги повторяются независимо для каждой валюты группы: упрощение долгового графа в разных валютах выполняется раздельно, поскольку взаимозачёт между обязательствами в разных валютах требовал бы введения курсов конвертации, что выходит за рамки текущей реализации.

**Шаг 1. Вычисление сальдо.** Для каждого участника в пределах рассматриваемой валюты вычисляется нетто-сальдо $b_{\text{cur}}(u)$ по формуле (1.7). Участник с положительным сальдо — кредитор, с отрицательным — должник, с нулевым — в расчёте не участвует.

**Шаг 2. Сортировка.** Кредиторы упорядочиваются по убыванию сальдо (наибольший кредитор — первый), должники — по убыванию абсолютного значения долга (наибольший должник — первый).

**Шаг 3. Жадное сопоставление.** Итеративно: наибольший должник переводит максимально возможную сумму наибольшему кредитору. Переводимая сумма равна минимуму из абсолютного значения долга должника и сальдо кредитора. После каждого шага обновляются сальдо обоих участников; участники с нулевым сальдо исключаются из дальнейшего рассмотрения. Итерации продолжаются до полного обнуления всех сальдо.

### Граница числа переводов

Пусть $N$ — число участников с ненулевым сальдо в рассматриваемой валюте. На каждой итерации перевод равен минимуму модулей сальдо должника и кредитора, поэтому хотя бы один из двух участников обнуляется и выбывает из дальнейшего рассмотрения. Согласно инварианту (1.8), суммарное сальдо оставшихся участников всегда равно нулю; поэтому когда остаётся единственный участник, его сальдо обязано быть нулевым, и последний перевод обнуляет сразу двух участников. Отсюда для обнуления $N$ участников достаточно не более $N-1$ переводов, тогда как попарное представление могло бы потребовать до $N(N-1)/2$.

Величина $N-1$ — верхняя граница числа переводов, а не гарантия их минимума: точная минимизация NP-трудна (см. постановку задачи), и жадная стратегия в отдельных конфигурациях даёт число переводов больше оптимального.

### Пример

Рассмотрим группу из трёх участников с итоговыми балансами из §1.6.5: Борис должен Алисе 1 500 коп., Чарли должен Алисе 4 000 коп., Чарли должен Борису 1 500 коп. Нетто-сальдо: Алиса = +5 500 коп., Борис = 0 коп. (он одновременно кредитор Чарли и должник Алисы на одинаковую сумму), Чарли = −5 500 коп. Поскольку сальдо Бориса равно нулю, жадный алгоритм исключает его из рассмотрения и сводит расчёты к одному переводу: Чарли → Алиса 5 500 коп., — вместо трёх попарных операций.

Аналогичный подход к упрощению долгового графа применяется в сервисе Splitwise [14] и описан в работе [3].

## 1.6.7 Валидационные инварианты API

В отличие от инвариантов на уровне СУБД, описанных в §1.5.6, API-уровень обеспечивает проверки бизнес-логики до обращения к базе данных, выступая первым рубежом валидации.

Корректность операций обеспечивается двухуровневой системой проверок: Pydantic-схемы осуществляют структурную валидацию на границе HTTP-запроса, тогда как бизнес-инварианты проверяются внутри транзакции базы данных.

**Инварианты создания расхода:**

- сумма долей участников равна полной сумме расхода: $\sum \text{splits[i].amount\_minor} = \text{amount\_minor}$ — для `POST /expenses` нарушение перехватывается сервисным слоем и возвращает `400 Bad Request`; для `PATCH /expenses/{id}` с одновременной корректировкой `amount_minor` и `splits` инвариант проверяется на уровне Pydantic-валидатора до входа в сервисный слой и возвращает `422 Unprocessable Content`;
- плательщик является активным участником группы (`status = active`);
- все пользователи из списка долей являются активными участниками группы;
- пользователь-актор (из заголовка `X-User-Id`) является активным участником группы;
- `amount_minor > 0` — нулевые и отрицательные суммы недопустимы;
- список долей не пуст и содержит не менее одного элемента.

**Инварианты создания погашения:**

- `from_user_id ≠ to_user_id` — пользователь не может погашать долг самому себе;
- оба участника (`from_user_id` и `to_user_id`) являются активными членами группы;
- актор является одним из участников операции (`from_user_id = X-User-Id`);
- `amount_minor ≤ текущий_долг(from → to, currency)` — запрещено «переплачивать» сверх зафиксированного долга; данный инвариант проверяется на уровне API при создании погашения, тогда как Шаг 3 алгоритма нормализации (§1.6.5) обеспечивает корректность для исторических данных и случаев параллельного создания расходов и погашений, когда состояние леджера может измениться между проверкой инварианта и пересчётом балансов;
- `amount_minor > 0`.

При нарушении любого из перечисленных бизнес-инвариантов на этапе обработки в сервисном слое возвращается ответ с кодом `400 Bad Request` и структурированным описанием ошибки, включающим поле-нарушитель и человекочитаемое сообщение. Структурные ошибки тела запроса, выявляемые на этапе Pydantic-валидации (некорректный тип поля, нарушение длины, дубликаты `user_id` в списке долей, а также инвариант суммы долей при PATCH-операции с одновременной правкой `amount_minor` и `splits`), обрабатываются FastAPI единообразно с возвратом кода `422 Unprocessable Content`. Разделение кодов согласуется с RFC 9110: `422` сигнализирует о синтаксически корректном, но семантически непригодном для обработки запросе, `400` — о запросе, отклонённом бизнес-валидацией сервисного слоя. Ответы об ошибках форматируются единообразно для всех сервисов, что упрощает обработку ошибок на стороне клиента.

Помимо проверок на этапе выполнения, инварианты финансовой модели верифицируются методом property-based тестирования (библиотека Hypothesis): равенство суммы долей сумме расхода (формула 1.4), сохранение суммарного сальдо по каждой валюте (формула 1.8), независимость результата от порядка операций, граница не более $N-1$ перевода с сохранением нетто-позиций и идемпотентность упрощения проверяются на автоматически генерируемых наборах расходов и погашений, а не на отдельных примерах. Методика и результаты тестирования приводятся в главе 2.

---

Контракт API сформирован так, чтобы разделить уровни ответственности и сохранить согласованность двух представлений одних и тех же данных. Валидация запроса разнесена по двум кодам ответа: код `422` возвращается при синтаксических нарушениях, выявляемых Pydantic на этапе парсинга тела, код `400` — при нарушении бизнес-инвариантов в сервисном слое; разграничение согласовано с RFC 9110 и переносит границу между «формой» и «смыслом» запроса в наблюдаемое клиентом поведение. Идемпотентность мутаций обеспечивается составным ключом `(idempotency_key, operation_scope, actor_user_id)`: повторное обращение с тем же `Idempotency-Key`, но изменённым телом, отличается от штатной ретрансляции по `request_hash` и не приводит к повторному исполнению бизнес-логики. Балансы предоставляются клиенту в двух согласованных представлениях — попарном (`GET /balances`) и greedy-минимизированном (`GET /balances/simplified`) — при общем леджере и общем инварианте сохранения суммарного сальдо (формула 1.8), что позволяет переключаться между прозрачностью долгов и удобством погашения без расхождения данных. Нормирование долей при равномерном распределении выполняется на уровне клиента, а сервер ограничивается проверкой инварианта суммы долей (формула 1.4); такое разделение оставляет за серверным слоем единственную ответственность за корректность ledger и позволяет менять стратегии распределения без изменения схемы базы данных. В параграфе 1.7 рассматриваются принципы стратегии развёртывания спроектированной системы, замыкающие архитектурное проектирование контуром эксплуатации.
