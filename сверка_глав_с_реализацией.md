## §1.6 Проектирование API и финансовой модели

Большинство утверждений соответствует реализации. Два расхождения требуют правки.

### Соответствует

- Шесть эндпоинтов auth (Таблица 1.4) — подтверждены роутером `backend/services/auth/app/main.py`.
- Семь эндпоинтов groups (Таблица 1.5) — подтверждены роутером groups.
- Эндпоинты expenses подтверждены: `POST /expenses`, `POST /settlements`, `GET /balances`, `GET /balances/simplified`, `GET /history` (`expenses/app/main.py`).
- Argon2 для паролей; JWT RS256 со стандартным набором claims без email; refresh-токен формата `ref_` + 24 случайных байта в base64, в БД — SHA-256 хэш (`auth/app/service.py:50,54,310`).
- Token-family rotation с детекцией компрометации.
- `Idempotency-Key` с составным ключом `(idempotency_key, operation_scope, actor_user_id)` и хэшем тела (`expenses/app/service.py:909-911`).
- Equal-split: floor(S/n) + остаток первому участнику; custom: явный список без модификации.
- Ledger-based расчёт балансов с четырьмя шагами (построение, погашения, нормализация, сортировка) — `_calculate_balances_from_records` в `expenses/app/service.py`.
- Greedy-минимизация — `_simplify_balances_from_records` (`service.py:806-856`).

### Расхождения, требующие правки

1. **§1.6.5 и §1.6.7: HTTP-код при нарушении инварианта суммы долей — 400, не 422.** Фактически: `raise ExpenseError("Sum of splits must match expense amount", status_code=400)` (`expenses/app/service.py:247` и дублирующая проверка `:422` в context-processing). Код `422` возвращается только Pydantic при структурных ошибках (например, дублирующиеся `user_id` в `splits`). Рекомендованная правка: либо привести текст к коду (§1.6.5: «нарушение инварианта формула (1.4) влечёт возврат `400 Bad Request`»; §1.6.7: «нарушение инварианта возвращает `400`, структурные ошибки тела запроса — `422`»), либо изменить код на `status_code=422` — последнее предпочтительнее семантически (RFC 9110: 422 Unprocessable Content для семантически валидного, но бизнес-некорректного запроса), но требует адаптации тестов и frontend-обработчиков ошибок.

2. **§1.6.4: пагинация `GET /history` — offset-based, не cursor-based.** Текст: «эндпоинт... предоставляет хронологический список всех расходов и погашений группы с поддержкой пагинации по курсору». Фактически (`expenses/app/main.py:159-188`) — параметры `limit: int = Query(default=HISTORY_DEFAULT_LIMIT)` и `offset: int = Query(default=0)`, ответ содержит `next_offset`. Рекомендованная правка: переформулировать §1.6.4 как «пагинация offset-based: параметры `limit` и `offset`, ответ возвращает `next_offset` для продолжения». Курсорная пагинация — направление развития v2 (упомянуть необязательно).

## §1.7 Стратегия развёртывания

Соответствует реализации в части концептуального описания и по большей части подкреплено готовыми файлами в репозитории:

- единая публичная точка входа на 80/443 — `docker-compose.prod.yml` публикует только эти порты, остальные сервисы скрыты через `ports: !reset []`;
- TLS на Nginx, HTTP→HTTPS-редирект, ACME challenge — `infra/nginx/nginx.prod.conf:22-47`, bootstrap-конфиг `nginx.bootstrap.conf` для первичного выпуска сертификата;
- автоматическое продление Let's Encrypt — certbot-сервис в `docker-compose.prod.yml:200-214` с периодом 12 ч;
- разделение фаз миграций и запуска — четыре migrate-контейнера в `docker-compose.prod.yml:119-193` с `depends_on service_completed_successfully`;
- `restart: unless-stopped` для всех сервисов в prod-compose;
- systemd-юниты — `infra/systemd/vkr-project.service`, `vkr-project-backup.service`, `vkr-project-backup.timer`;
- backup PostgreSQL и retention 14 дней — `infra/scripts/backup-postgres.sh:33` (`find ... -mtime "+$BACKUP_RETAIN" -delete`);
- init-роли БД — `infra/postgres/init/01-init-roles.sh`;
- healthchecks через schema-guard — `docker-compose.yml:107-108` и `docker-compose.prod.yml:99-103`.

Только в `deploy_vps.md` (как пошаговая инструкция, специфичная для целевого сервера, без конфигурационного файла в репозитории):

- настройка SSH-hardening (`PermitRootLogin no`, отключение пароля, `AllowUsers deploy`) — раздел 8;
- настройка UFW (порты 22/80/443) — раздел 9;
- swap 1 ГБ + `vm.swappiness=10` — раздел 10;
- конфигурация `/etc/docker/daemon.json` (`max-size`, `max-file`) для log-rotation — раздел 12.

Это решение обоснованно: указанные конфигурации специфичны для конкретного хоста и исполняются администратором при первичной подготовке сервера.
